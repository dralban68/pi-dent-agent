# Sandboxing agent-generated JavaScript

Research on how the `Script` tool can run agent-generated code with controlled disk and network
access. Read it before speccing or changing the `Script` tool's execution model. The requirements:
the code is generated by agents and treated as potentially hostile — a prompt injection in a file
or web page can steer what the agent writes — it must get controlled access to disk and network,
and it must work on Windows as well as macOS and Linux.

The research is desk research: web sources and READMEs, nothing run. Every claim below carries
its source; claims no source verifies are marked as such.

## Ruled out

| Option                                            | Why ruled out                                                                                                                                                                                                                                                         |
| ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `node:vm`                                         | The Node docs say it is not a security mechanism ([nodejs.org/api/vm](https://nodejs.org/api/vm.html)).                                                                                                                                                               |
| `vm2`                                             | Maintained again on 3.x, but new critical sandbox escapes kept landing in 2026.                                                                                                                                                                                       |
| Node `--permission`                               | Stable since 22.13, but the docs call it a "seat belt" that malicious code can bypass ([nodejs.org/api/permissions](https://nodejs.org/api/permissions.html)); workers can drop it through `execArgv`.                                                                |
| `isolated-vm`                                     | Maintenance mode; a native addon needing `--no-node-snapshot` on Node 20+; a leaked `Reference` gives full access back to Node ([github.com/laverdet/isolated-vm](https://github.com/laverdet/isolated-vm)).                                                          |
| Secure Exec (Rivet, npm `secure-exec`)            | The best functional fit — V8 isolates in a Rust sidecar with a virtual kernel, mounts, per-host network rules — but Linux (glibc) and macOS only, so it fails the Windows requirement. Also young (first published February 2026, 0.2.22) with no public audit found. |
| Javy, StarlingMonkey, Boa, Porffor, Static Hermes | Wrong deployment model or too immature.                                                                                                                                                                                                                               |

## Recommended: QuickJS in WebAssembly with a small host API

QuickJS compiled to WebAssembly, with a small set of host functions:

- Pure WASM, no native binary, the same on Windows, macOS, and Linux.
- The script has no ambient access: every read, write, list, and fetch is a host function that
  checks a path and host allowlist, so it is deny-by-default by construction and each refusal can
  be reported as an error.

Two libraries:

- [`@sebastianwessel/quickjs`](https://github.com/sebastianwessel/quickjs)
  ([docs](https://sebastianwessel.github.io/quickjs/docs/)): a ready-made sandbox on
  `quickjs-emscripten-core` + quickjs-ng. Opt-in `allowFetch`, `allowFs` (a virtual file system
  only, via `mountFs`), `env` for host functions, `executionTimeout`, `memoryLimit`, and a
  `{ ok, data }` result. Starting point: both `allow*` off, with pi-dent's own host functions
  through `env`.
- [`quickjs-emscripten`](https://github.com/justjake/quickjs-emscripten): low-level bindings;
  nothing exposed by default, manual handle disposal. A smaller surface to audit; the fallback
  if the wrapper is too much.

The cost: agents write plain ECMAScript against the host API — no Node built-ins, no npm
packages, no `Intl`/`Temporal`/`WebAssembly` in the guest — and an interpreter several times
slower than V8.

## Known gaps to verify

Nothing below is verified; it is a competitor's account — [Rivet's comparison page
](https://rivet.dev/secure-exec/docs/comparison/quickjs/) and
[security notes](https://rivet.dev/secure-exec/docs/security/) — citing open quickjs-emscripten
issues. Verify on the current release before relying on any engine-level limit:

- The memory limit is not enforced for some allocations: 500 MB of strings under an 8 MB limit
  (issues [#271](https://github.com/justjake/quickjs-emscripten/issues/271),
  [#255](https://github.com/justjake/quickjs-emscripten/issues/255)).
- The interrupt handler is not consulted inside long built-ins: a 50 ms deadline ran 882 ms
  (issue [#219](https://github.com/justjake/quickjs-emscripten/issues/219)).
- Guest code blocks the thread it runs on; guest promises advance only on `executePendingJobs()`.
- The Asyncify build is about 2× the size, much slower, and allows one suspended call per
  module; prefer the normal build with promise-returning host functions.
- Unaudited, pre-1.0.

Consequence: run the engine in a worker or child process with an outer kill timer and its own
memory cap (`resourceLimits`), and do not rely on the engine's limits alone.

## Fallback: Deno as a child process

Run Deno as a child process with per-path and per-host permission flags: it runs Node-style code
on Windows too, at the cost of shipping a binary per platform. Not researched: this is the
researching session's own knowledge, with no sources behind it.
